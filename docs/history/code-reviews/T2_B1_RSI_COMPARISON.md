# T2-B1 · RSI 过热口径对比(单一 vs daily/weekly)+ 建议

> **日期：2026-06-02** ｜ 对齐 module B 的 B1「RSI 过热」。这是 T5 观察到 WATCH↔HOLD
> 翻转的直接驱动项。下面是两边的**精确逻辑、对 status 的具体影响、我的建议**。

## 两边精确逻辑

### 包(`module_b._rsi_overheat`)——单一日线 RSI,所有标的同一套
```
rsi = rsi14            # 仅日线
rsi >= 80 -> 5 分
rsi >= 75 -> 3 分
rsi >= 70 -> 1 分
否则       -> 0 分
```
- 只看**日线 RSI**;无 weekly、无雷达;**所有标的同阈值**。

### 单体(`escape_top_system` B1)——日线 + 第二维(weekly/雷达),分标的
```
MSTR:   daily>82 ->4 ; daily>75 ->2 ; 否则 0
      + weekly>78 ->2 ; weekly>72 ->1
FNGU/SOXL: daily>85 ->4 ; daily>78 ->2 ; 否则 0
      + 雷达(FNGS/SOXX) rsi>80 ->2 ; >72 ->1
合计封顶 5
```
- 看**日线 + 第二维**(MSTR 用周线;FNGU/SOXL 用对应雷达 RSI);**阈值分标的且更高**。

## 对 status 的具体影响(实测案例)

T5 里 **FNGU 2026-05-22:单体 WATCH,包 HOLD**。该日 B1 输入:`daily≈68.0, weekly≈78.7`。

| | 包 | 单体(FNGU) |
|---|---|---|
| 看的输入 | 仅 daily=68.0 | daily=68.0 + 第二维(weekly/雷达 ≈78.7) |
| B1 得分 | 68<70 → **0 分** | daily 68(<78→0)+ 第二维 78.7(>72 → +1/+2) → **1–2 分** |
| 结果 | B 偏低 → **HOLD** | B 抬高 → 越过 WATCH 门 → **WATCH** |

**根因一句话**:包的"只看日线 RSI"**对周线/雷达层面的过热完全失明**;FNGU 日线才 68(看似不热)
但周线已 78.7(实际过热),单体捕捉到了、包漏掉了 → 一个判 WATCH,一个判 HOLD。

## 我的建议:以**单体口径为准**(把 daily+weekly/雷达 移植进包)

**理由(风控向)**:
1. 这是**逃顶/防守**系统——**漏报顶部信号(误判 HOLD)是最危险的失败模式**。周线过热是
   比日线更强、更慢、更可信的顶部信号;包只看日线会系统性漏掉"日线已回但中期仍过热"的危险态。
2. 单体的**分标的、更高阈值**是 v25 校准的产物(杠杆 ETF 波动大,日线 RSI 阈值理应更高);
   包的"统一 70/75/80"是通用占位,未针对标的校准。
3. 多时间框架(daily+weekly)是成熟的过热判定实践;单一日线是简化,信息更少、更噪。

**因此**:T2-B1 采用单体口径,工作 = 在**包的特征层补 `rsi14_weekly` 和雷达 RSI**,并把
B1 改成"日线 + 第二维、分标的阈值、封顶 5"。采用后应纳入包的分数概率校准复核。

**代价/权衡(诚实说)**:
- 需给包接 weekly RSI(history 周线 resample)+ 雷达 RSI 特征——属 T1 已识别的"缺失特征"补全。
- 单体那行 reason 串 `f"daily=…, weekly=…"` 对 FNGU/SOXL 其实有点误导(实际算的是雷达 RSI,
  显示的是 weekly)——移植时**顺手修正显示**,别把 bug 一起搬过去。
- 若反过来选"包口径为准"(单一日线):实现更简单,但**等于让生产系统在防守上变迟钝**,
  我不建议。
